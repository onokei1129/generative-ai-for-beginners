# 復元訓練 第1回 実施記録

バックアップは「取れていること」ではなく「戻せること」を確認して初めて意味を持つため、
[運用手引き §7](./operations-guide.md#7-復元と復元訓練) の手順にしたがって復元訓練を実施した。

| 項目 | 内容 |
| --- | --- |
| 実施日 | 2026-07-28 |
| 対象 | 検証環境（PostgreSQL 16 / ローカルオブジェクトストレージ / 4CPU） |
| 手順 | `ops/backup.sh` → 別データベースへ `ops/restore.sh` → `ops/verify.py` → アプリ起動確認 |
| データ量 | 名刺 5 件 / 画像 24 件 / 監査ログ 9 件 ＋ アーカイブ 1 本（40 件） |
| 結果 | **成功**（ただし手順の不具合を1件検出。修正済み） |

| 手順 | 所要 |

> 本番相当のデータ量（名刺 3,000 件／画像 9,000 件／約 10GB）では、
> `pg_dump` と画像の展開が支配的になる。上記はあくまで手順が通ることの確認であり、
> RTO（論点O の初期案 4 営業時間）の妥当性は本番相当のデータ量で再測定する必要がある。
> **次回の訓練で、本番想定のデータ量を投入して所要時間を測ることを課題とする。**

## 3. 検出した不具合と対応

### 画像が設定と違う場所へ復元される（修正済み）

**現象**　復元先のオブジェクト保存先を `BCARDS_STORAGE_DIR=/tmp/drill-objects` に指定して
`ops/restore.sh` を実行したところ、画像は `/tmp/objects` に展開され、
指定した `/tmp/drill-objects` は作成されなかった。

**原因**　`ops/backup.sh` が保存先ディレクトリ名を含めて tar に固めていたため
（`objects/cards/...`）、復元時にその名前のディレクトリが作られていた。
取得元と復元先でディレクトリ名が違う場合に、必ず間違った場所へ展開される。

**影響**　本番機と同じディレクトリ名で復元する限り顕在化しないが、
別サーバーへ復元する場合や、検証用に別ディレクトリへ戻す場合に画像が失われたように見える。
実際、この訓練では `ops/verify.py` が全件欠損として検出した。

**対応**　保存先ディレクトリ名を含めず中身だけを固めるよう `ops/backup.sh` を変更し、
`ops/restore.sh` は指定された保存先へ直接展開するようにした。
旧書式のアーカイブ（`objects/` を含むもの）も判別して展開できるようにしてある。
修正後に同じ手順をやり直し、指定どおりの場所へ復元されることを確認した。

> この不具合は自動テストでは見つからず、実際に手順を通したことで見つかった。
> 訓練を定期的に行う意味がここにある。

## 4. 次回への申し送り

1. 本番相当のデータ量（名刺 3,000 件／画像約 10GB）で所要時間を測り、RTO を確定する（論点O）
2. S3 運用に切り替えた後、オブジェクトストレージ側の復元手順でも同じ訓練を行う
3. 復元先を別サーバーにして、ネットワーク越しの転送時間を含めて測る
4. 実施頻度は四半期に1回。次回は 2026年10月
