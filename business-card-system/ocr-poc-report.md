# OCR精度 PoC 報告

**[open-issues-v0.3.md 論点C](./open-issues-v0.3.md#論点cocrサービスの選定) に対する第1回計測**

---

## 1. この報告の位置づけ

論点Cは「OCRサービスをどう選ぶか」だった。今回のPoCで確認したのは次の2点。

1. **どの構成が精度・時間・費用で有利か**を、推測ではなく**実測**で比較できる仕組みを作ること
2. その仕組みで現行実装を測り、**改善できる箇所を特定して直すこと**

計測は再現可能なコードとして `app/poc/` に置いてある。実名刺が用意できた段階で、
同じコマンドに `--real` を付けるだけで本番相当のデータで測り直せる。

```bash
cd app
./.venv/bin/python -m poc.runner --out ../ocr-poc-report.md          # 合成サンプル
./.venv/bin/python -m poc.runner --real ./poc/samples --out ../x.md  # 実名刺
```

> **重要な前提**：今回のサンプルは**合成画像**である。実名刺のフォント・紙質・印刷のかすれ・
> 逆光などは再現できていないため、**絶対値は実データでの精度を保証しない**。
> 構成間の相対比較と、改善の効果測定に使うことを目的としている。

## 2. 結論

| # | 結論 | 根拠 |
| --- | --- | --- |
| 1 | **表示用の画像補正をOCRに掛けてはいけない** | 補正あり 41.4% → 補正を外して 53.8%（**+12.4ポイント**） |
| 2 | 傾き補正は**1.5度未満では掛けない**ほうがよい | 微小回転の再サンプリングで文字が甘くなり、-5ポイント |
| 3 | 縦長の名刺を横長に自動回転してはいけない | 縦書き名刺のOCRを壊す。回転をやめて縦書き言語データを併用 |
| 4 | 縦書き名刺は**依然として最も苦手**（修正10項目/枚） | tesseractの限界。クラウドOCRまたはLLM抽出で再評価が必要 |
| 5 | ふりがな（せい・めい）は**ルールベースではほぼ0%**（せい0%・めい6%） | OCRが語の途中に空白を入れるため、規則では姓名に割り当てられない。LLM抽出（方式2）で改善が見込める領域 |

**実装済みの改善**：結論1〜3はアプリ本体に反映済み。
表示用画像とOCR用画像を分離し（`services/images.py`）、原本として保存するのは補正前の画像に変更した。
これにより再処理時のOCR精度も落ちない。

**未確定のまま残ること**：方式2（LLM抽出）とクラウドOCRは、この環境に認証情報が無いため未計測。
アダプタの実装と計測の受け皿は用意してあるので、鍵を設定すれば同じ手順で数値が出る。

## 4. 何が起きていたか（改善の内訳）

### 4.1 表示用の補正がOCRを壊していた

改善前は、1枚の補正済み画像を「表示にもOCRにも」使っていた。工程ごとに切り分けて測ると：

| 工程 | 項目正答率 |
| --- | ---: |
| 生ページ | 43.4% |
| ＋名刺の切り出し（台形補正） | 43.4% |
| ＋傾き補正（0.3度以上で回転） | 38.1% |
| ＋明るさ・影の補正（CLAHE＋影除去） | 34.0% |

人が見やすくするための補正（コントラスト強調・影の除去）は、OCRにとっては文字の輪郭を
なまらせる処理でしかなかった。**表示用とOCR用を分ければ、どちらも犠牲にしない。**

### 4.2 効果がなかった／悪化した施策

「やってみたが採用しなかった」ものも記録しておく。同じ検討を繰り返さないため。

| 施策 | 結果 | 判断 |
| --- | ---: | --- |
| 二値化（大津の方法） | 25.8% | 不採用（大幅悪化） |
| 適応的二値化 | 32.1% | 不採用 |
| アンシャープマスク | 36.3% | 不採用 |
| 高解像度化（長辺2200px）＋シャープ化 | 30.8% | 不採用（悪化かつ処理時間2倍） |
| 弱いコントラスト補正のみ | 36.3% | 不採用 |
| 縦長画像の向き総当たり（0/90/270度でOCRし最良を採用） | 変化なし | 不採用（時間だけ増える） |
| 向き検出(OSD)による90度単位の回転補正 | 回転した名刺で 2項目 → 14項目 | **採用**（下記4.3） |
| ページ分割モード psm 5 の追加 | 変化なし | 不採用 |
| 縦書き言語データ `jpn_vert` の併用 | +0.5ポイント | **採用**（処理時間は +1.1秒/枚） |


### 4.3 90度回った名刺は、OCRがほぼ何も読めない

実テストで「名刺として正しく仕分けられているのに、項目が1つも取れない」という報告があった。
原本を見ると、読み取り機に横向きに置いたために画像ごと90度回っていた。
人が見れば読めるので「OCRが弱い」と誤解されやすいが、原因は別物だった。

| 入力 | 取れた項目 |
| --- | ---: |
| 正立 | 14 / 14 |
| 90度回転 | 2 / 14 |

傾き補正（`deskew`）が扱うのは数度のズレで、90度は対象外だった。
tesseract の向き検出（OSD）で90度単位の回転だけを別に直すようにした（`services/orientation.py`）。
補正後は 0/90/180/270度のいずれで入れても 14/14 に戻る。

**縦書き名刺を巻き添えにしないこと**が最大の懸念だった（形だけで回すと壊れるのは4.2で不採用にしたとおり）。
OSDは字の形から向きを読むため縦書きも正立と判定し、PoCサンプル16枚（縦書きのscan/photoを含む）は
**全て回転0度**、つまり1枚も誤って回さないことを確認したうえで採用した。
確信度が低い判定は採用しない（誤って回す害のほうが大きいため）。


### 4.4 「OCRは読めているのに、取り出し方で落としていた」3件

項目ごとの正答率を1枚ずつ突き合わせたところ、OCRの限界ではなく
**こちらの取り出し方の問題**で落としていたものが3件あった。

| 項目 | OCRが読んだ文字 | 取れていた値 | 原因 |
| --- | --- | --- | --- |
| URL | `https://www. example. co. jp` | `https://www.` | ドットの後の空白で正規表現が止まっていた（16枚中4枚） |
| メール | `taro, yamada@example.co.jp` | `yamada@example.co.jp` | ローカル部のドットがカンマと読まれ、先頭が丸ごと落ちていた |
| 住所 | `7100-0001 東京都…` | `7 東京都…` | 〒 が `7` と読まれ、郵便番号を抜いた残りに付いてきていた |

いずれも直した。**総合 45.2% → 51.0%**（1枚あたりの修正項目数 7.2 → 6.4）。

| 項目 | 修正前 | 修正後 |
| --- | ---: | ---: |
| 住所 | 38% | **69%** |
| URL | 17% | **50%** |
| メール | 44% | **62%** |

直しすぎると別のものを壊すため、次の3つは壊れないことを確認したうえで入れている。

- `info@a.co.jp, sales@a.co.jp` のようにメールを2つ並べた行で、前のアドレスを巻き込まない
- `7-1-1 Chiyoda, Tokyo 100-0001` のような英字表記で、番地の `7` を消さない
- `https://tech.example.jp Mobile 090-…` で、URLに電話番号を繋げない


### 4.5 1行に並んだ部署と役職を分けていなかった

名刺は「開発部 主任」のように部署と役職を1行に印字することが多い。
部署がその行を丸ごと取っていたため、**1行で2項目とも落としていた**。

| OCRが読んだ行 | 部署（正解） | 部署（取得） | 役職（取得） |
| --- | --- | --- | --- |
| `開発部 主任` | `開発部` | `開発部主任` | `開発部主任` |
| `営業本部 第一営業部 部長` | `営業本部 第一営業部` | `営業本部第一営業部部長` | `部長` |

役職の語が行末側にあり、その手前に部署の語がある場合に分けるようにした。
**総合 51.0% → 52.9%**（部署 50% → 62%、役職 50% → 62%）。

切りすぎると別の壊れ方をするため、次を確認したうえで入れている。

- `本部長` は `本部` を含むが部署ではない（行全体が役職の語と一致する場合は部署にしない）
- `Sales Department` の `Sales` を役職にしない（役職の語が行頭にある場合は分けない）
- `シニアエンジニア` を `エンジニア` に切らない（手前に部署の語が無い場合は分けない）


### 4.6 海外名刺の電話番号を1件も拾えていなかった

海外名刺が多いという前提を確認する過程で見つけた。国番号つきの番号を
**`+81` だけ**見ていたため、それ以外の国の電話番号を拾えていなかった。

| 名刺 | 電話 |
| --- | --- |
| `TEL +1 212-555-0100`（米国） | 空 |
| `TEL +7 495 123-45-67`（ロシア） | 空 |
| `Tel: +44 (0)20 7123 4567`（英国） | 空 |

英語の名刺は他の6項目が取れていたため、**電話だけが欠ける**形で表面化していた。
国番号のあとを「数字と区切りの並び」として扱うようにし、上記すべてを拾えるようにした
（桁数は E.164 の15桁まで）。日本語名刺の精度は 52.9% で変化なし。

**あわせて重複人物の判定も直した。** `+81 90-1234-5678` と `090-1234-5678` は
同じ番号だが別の値になっていたため、同じ人が2枚の名刺で別人として登録されていた。
正規形を国内表記に揃え、既存データは移行で詰め替える（`a4f18b2c7e05`）。
国際表記の `(0)`（国内でのみ0を付ける慣習表記）も揃えている。

他国の携帯は見分け方が国ごとに違うため、国番号を残したまま「電話」に入れる。
誤って「携帯」に入れるより無害という判断。


### 4.7 外国名・英字表記の名刺で、6項目を取りこぼしていた

実データ（チリの制作会社の名刺）で、記載のある7項目のうち3項目しか
取れていなかった。**OCRは読めていて、抽出側で落としていた。**

| 項目 | 修正前 | 修正後 | 原因 |
| --- | --- | --- | --- |
| 姓・名 | `AONE` / `GAMES` | `パトリシオ` / `バスケス` | ロゴの英字を氏名にしていた |
| ふりがな | `パトリシオ` / `バスケス` | 空 | カタカナの氏名をふりがな扱いにし、姓名が空になっていた |
| 会社名 | 空 | `AONE GAMES` | 法人格の語（`株式会社`・`Inc.`）を含まないため拾えなかった |
| 役職 | `プロデューサー` | `エグゼクティブ・プロデューサー` | 和英併記の行から語だけを取り、修飾を捨てていた |
| 住所 | 空 | `Santa Beatriz 111 of 1008, …` | 都道府県の語が無いため拾えなかった |

直した規則は次の5つ。

1. **ふりがなはひらがなに限る。** カタカナだけの行は氏名として扱う
   （外国名の名刺はカタカナで氏名を印字する）
2. **全部大文字の英字は氏名にしない。** ロゴや社名の綴り。人名は通常そう書かない
3. **法人格の語が無い社名は、メールのドメインとの一致で見つける**
   （`AONE GAMES` ↔ `patricio@aonegames.com`）。一致しなければ空のままにする
4. **役職は和英併記の区切り（`/`）で日本語側を採り**、修飾を含む全体を残す
5. **住所が他から取れないときだけ**、数字を含む複数語の最長行を住所とする
   （メール・URL・語数の少ない行は除く）

カタカナ名の分け方も直した。OCRが語の途中に空白を入れるため
（`パトリシオ　バスケス` → `パト リシオ バスケス`）、先頭の空白で切って
`パト` / `リシオ バスケス` になっていた。どこが語の切れ目かは字面では
決まらないので、**長さの釣り合いがいちばん良い位置**で分ける。
日本語・英字の氏名の分け方は変えていない。

日本語の名刺への影響はなく、合成サンプルの総合は 52.9% で変わらない
（この名刺の型が合成サンプルに無いため、数値には表れない）。

### 4.8 電話番号を郵便番号として登録していた

実データ（韓国の方の名刺）で、記載のある8項目のうち4項目が空、
うち2項目に**誤った値**が入っていた。空欄より悪い。

| 項目 | 修正前 | 修正後 | 原因 |
| --- | --- | --- | --- |
| 郵便番号 | `070-9385` | `580-0021` | 携帯番号 `070-9385-4004` の前半を郵便番号として取っていた |
| 住所 | `-4004` | `大阪府松原市高見の里六丁目7-18` | 上の残り。本来の住所行は `Add` のラベルごと未使用のまま捨てていた |
| 電話 | 空 | `050-3110-2873` | `Tel 050-…` を携帯として扱い、先に入っていた携帯に押し出されて消えた |
| 携帯 | `070-9385-4004` | 同じ | `HP` を携帯のラベルとして知らず、先頭3桁だけで判定していた |

直した規則は次の4つ。

1. **郵便番号は前後を見る。** 後ろに数字や区切りが続くならその番号の途中
   （`070-9385`**-4004**）。前に数字が接している場合も同様。ただし
   〒 の読み違え（`7100-0001`）は例外として通す
2. **`HP`（handphone）を携帯のラベルに加える。** 韓国・台湾・東南アジアの
   名刺で使われる。英字のラベルは語の先頭に限る（`graphpad` の `hp` に
   当たらないように。`telephone` の `tel` は従来どおり拾う）
3. **ラベルが直に付いている番号は、ラベルを信じる。** `050` はIP電話で
   携帯ではないため先頭3桁の一覧から外し、`Tel 050-…` は電話として扱う。
   先頭3桁での見直しは、ラベルと番号の間に別の番号が挟まる場合
   （`TEL 03-… / 090-…`）に限る
4. **住所のラベル（`Add` `Address` `住所` `所在地`）を値に含めない。**
   郵便番号も都道府県も無い住所は、このラベルを頼りに拾う
   （英字の語は後ろに文字が続くものを除く。`Addison Road` を
   `ison Road` にしないため）

ラベルの照合を見直したついでに、隣接する2つの取りこぼしも直した。

- **`代表取締役` の `代表` を電話のラベルと数えていた。** 代表電話のラベル
  `代表` は残したまま、役職の一部（取締役・理事・社員が続く形）のときだけ
  数えないようにした
- **役職と番号を1行に印字した名刺**（`代表取締役 090-1234-5678`）で、
  番号を採った時点で行ごと使用済みにし、役職が空になっていた。番号と
  ラベルを外した残りから役職を探す

合成サンプルでも、郵便番号の判定を厳しくした副作用として住所が2枚改善した。
桁が合わず郵便番号として取れなかった `〒…` の残骸（`〒5390-0091 大阪府…`）を
住所から外し、読み崩れたURLの行（`tal 7 <kaido-foods.example`）を住所に
入れないようにしたため。

総合 52.9% → **53.8%**、修正項目 6.19 → **6.06 項目/枚**、住所 69% → **81%**。
なお郵便番号が読めなかった枚では、以前は誤った番号（FAX番号の一部）が
入っていたのに対し、いまは空欄になる。数値上はどちらも不正解だが、
**空欄のほうが入力する人には直しやすい**という判断。

### 4.9 海外の法人格を知らないため、社名が空になっていた

5.1 の計測で分かっていた「言語データを入れても項目が埋まらない」の本体。
法人格の辞書が `株式会社` と `Inc.` しか持たず、次のような社名を1件も
拾えていなかった。

| 名刺 | 修正前 | 修正後 |
| --- | --- | --- |
| `주식회사 오모로봇`（韓国） | 空 | `주식회사 오모로봇` |
| `欧姆机器人有限公司`（中国） | 空 | `欧姆机器人有限公司` |
| `ООО «Ромашка»`（ロシア） | 空 | `ООО «Ромашка»` |
| `Omorobot GmbH`（ドイツ） | 空 | `Omorobot GmbH` |

`주식회사` `(주)` `㈜` `유한회사` `有限公司` `股份公司` `集团` `有限責任公司`
`ООО` `ЗАО` `ОАО` `ПАО` `GmbH` `S.A.` `SARL` `B.V.` `N.V.` `Sdn Bhd` `PLC` `LLP`
を辞書に加えた。**`AG`・`SA`・`AB` のような2文字の略号は入れていない**
（`MANAGER` の中の `AG` のように別の語の一部に当たるため）。

3文字以上でも同じ問題は起きる。`S.A.` は住所の `U.S.A.` に当たり、
**住所の行が社名として登録されていた**（`123 Main St, Chicago, U.S.A.`）。
英字の略号は、直前が英字またはドットのときは数えないようにした
（`Acme S.A.` は数える。`U.S.A.` は数えない）。

**あわせて空白の扱いを文字体系ごとに分けた。** OCRの日本語出力は語の途中に
空白を入れるので消していたが、その規則を「ASCII以外の文字どうしの間」に
掛けていたため、ハングルやキリル文字の**語の区切り**まで消していた。

| 印字 | 修正前 | 修正後 |
| --- | --- | --- |
| `株式会社 サンプル 商事` | `株式会社サンプル商事` | 同じ（変えない） |
| `주식회사 오모로봇` | `주식회사오모로봇` | `주식회사 오모로봇` |
| `ООО «Ромашка»` | `ООО«Ромашка»` | `ООО «Ромашка»` |

空白を消す対象を、かな・漢字・全角記号に限った。日本語・中国語は語を空白で
区切らないが、ハングル・キリル文字・英字は区切るため。

法人格を外した照合値（`normalize_company`）も揃えているので、`주식회사 오모로봇`
と `오모로봇` は同じ会社として扱われる（重複人物・重複会社の判定に使う）。

## 5. 残っている弱点と、次に測るべきこと

| 弱点 | 現状 | 次の検証 |
| --- | --- | --- |
| 縦書き名刺 | 修正10.0項目/枚。実質的に手入力に近い | クラウドOCR・LLM抽出で再計測。改善しなければ「縦書きは手入力」と運用で割り切る判断も要る |
| ふりがな | せい0%・めい6%。OCRが `や まだ た ろう` のように語の途中で空白を入れるため、規則では姓と名に割れない | LLM抽出（方式2）は画像のレイアウトを見て判断できるため改善が見込める |
| URL | 50%。ドットの後の空白は詰めたが、まだ半分は読み取り自体が崩れている | LLM抽出で補正できる可能性 |
| 装飾の多い名刺 | 修正6.0項目/枚 | 背景色・ロゴが認識を妨げている。クラウドOCRの領域検出に期待 |
| 住所 | 69% | 残りは番地の数字・ハイフンの誤認識が中心 |

### 5.1 海外名刺への対応（言語データと項目分離は別問題）

韓国語・中国語・ロシア語の言語データを入れて実測した。

| 構成 | 日本語名刺の正答率 | 処理時間/枚 |
| --- | ---: | ---: |
| 現行 `jpn+jpn_vert+eng` | 52.9% | 3.01 秒 |
| ＋韓国語＋中国語＋ロシア語 | 53.8% | 4.32 秒 |

（絶対値は 4.8 の修正前の測定。言語データによる差分として読む）

**精度は落ちない**（当初は劣化を見込んでいたが外れた）。ただし**処理時間が44%増える**。

より重要なのは、**言語データを入れても項目が埋まらない**こと。

| 名刺 | 取れた項目（7項目中） | 落ちたもの |
| --- | ---: | --- |
| 英語 | 6 | 電話（4.6で対応済み） |
| 中国語 | 4 | 会社名・役職 |
| 韓国語 | 3 | 会社名・役職・氏名 |
| ロシア語 | 1 | ほぼ全部 |

法人格の辞書が `株式会社` / `Inc.` しか持たないためで、`주식회사`・`有限公司`・`ООО`
は未登録。**言語データの追加と、項目分離の対応は別作業**であり、後者が本体。

したがって全言語を常時読み込むのではなく、`BCARDS_OCR_LANGUAGES` で
**必要なときだけ足せる**現在の形を維持する。辞書の拡充は、実データで
どの言語の名刺が何枚あるかを数えてから優先順位を決める。

### 5.2 LLM抽出（方式2）の計測手順

実装は完了している（`app/src/bcards/services/ocr/llm_extractor.py`）。
Claude API に名刺画像とOCRテキストの両方を渡し、JSON Schema による構造化出力で項目を受け取る。

```bash
export ANTHROPIC_API_KEY=...        # または ant auth login
cd app

# 構成Eだけを計測する（既存の構成A〜Dの再計測を省いて費用と時間を抑える）
./.venv/bin/python -m poc.runner --only E --out ../ocr-poc-report-llm.md

# 全構成を並べて比較する場合
./.venv/bin/python -m poc.runner --out ../ocr-poc-report.md

# エフォートを振って精度と費用の関係を見る場合
./.venv/bin/python -m poc.runner --only E --llm-effort medium --out /tmp/e-medium.md
```

計測すると、構成Eの行に**正答率・処理時間・1枚あたりの費用（トークン数から算出）**が入る。
モデルは既定で `claude-opus-5`、エフォートは `low`（抽出は単純なタスクのため）。
`--llm-model` / `--llm-effort`、または `BCARDS_LLM_MODEL` / `BCARDS_LLM_EFFORT` で変更できる。

アダプタ自体は認証情報が無くても検証済みで、`app/tests/test_llm_extractor.py` が
HTTPトランスポートを差し替えて次を確認している。

- 名刺画像（base64 JPEG）とOCRテキストの両方を送っていること
- 構造化出力のスキーマに全項目が含まれ、余分なキーを許さないこと
- 長辺1600pxを超える画像は縮小してから送ること（費用と転送量の抑制）
- 拒否応答を抽出結果として扱わないこと
- `auto` ではLLMが失敗してもルールベースへ退避し、取込が止まらないこと

したがって鍵を設定すれば、追加の実装なしにそのまま計測に入れる。

### 5.3 クラウドOCRの計測手順

Azure AI Document Intelligence のアダプタは実装済み（`BCARDS_OCR_PROVIDER=azure`）。
Google Document AI / Amazon Textract を比較する場合は
`services/ocr/providers.py` に同じインターフェースでクラスを追加する（30行程度）。
