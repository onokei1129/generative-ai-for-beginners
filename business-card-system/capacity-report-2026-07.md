非機能要件（[画面・機能一覧 §5](./screens-and-functions-v0.3.md#5-非機能要件ver03で確定が必要)）のうち
「要確定」としていた **検索応答時間** と **RPO / RTO（論点O）** を確定するため、
本番相当のデータ量を投入して実測した。

| 項目 | 内容 |
| --- | --- |
| 実施日 | 2026-07-28 |
| 環境 | PostgreSQL 16 / ローカルオブジェクトストレージ / 4CPU・15GB RAM |
| データ量 | 名刺 10,000 件 / 人物 10,000 件 / 会社 1,442 社 / 画像 30,000 件（1.1GB） |
| 参考測定 | 名刺 100,000 件（§7）、同時アクセス（§6） |
| 投入方法 | `app/ops/loadgen.py`（架空データ生成ツール） |
| 測定方法 | `app/ops/bench.py`（単独）、`app/ops/bench_concurrent.py`（同時アクセス） |

要件§3 の想定は年間3,000枚のため、10,000件は **約3.3年ぶんの蓄積**にあたる。
100,000件は約33年ぶんで、現実的な運用期間を超えるが、
初版で立てた予測を検証するために測定した（§7）。

## 1. 結論

| 非機能要件 | 目標 | 実測 | 判定 |
| --- | --- | --- | --- |
| 検索応答時間 | 1万件規模で2秒以内 | 最悪 **337 ms**（単独）／**322 ms**（5人同時＋取込2人） | **達成**（目標の 1/6） |
| 復旧時間（RTO） | 4営業時間（初期案） | **約2分**（バックアップ取得を除けば約45秒） | **達成**（大幅な余裕） |
| 目標復旧時点（RPO） | 24時間 | 日次バックアップで24時間 | 達成 |

いずれも目標を大きく下回った。**RTO 4営業時間は保守的すぎる**ため、
実態に合わせて短縮できる（後述の §5 を参照）。

ただし、この測定で**性能問題を3件検出**し、いずれも修正した。

| 問題 | 効果 | 記載 |
| --- | --- | --- |
| ホーム画面がストレージ全体を毎回走査していた | 551ms → 41ms | §4.1 |
| CSV出力が名刺1件ごとに連絡先を読み直していた（N+1） | 12.05秒 → 2.85秒 | §4.2 |
| 10万件で該当なし検索が要件を超えていた | 2,158ms → 382ms | §7 |

いずれも件数が増えるほど悪化する作りで、小さなデータでは表面化しなかった。

## 4. 検出した性能問題（修正済み）

どちらも**件数に比例して悪化する**作りで、小さなデータでは気づけないものだった。

### 4.1 ホーム画面がストレージ全体を毎回走査していた

**現象**　ホーム画面の応答が 551 ms。うち約 490 ms がストレージ使用量の集計。

**原因**　容量アラートの判定に使う使用量を、画面表示のたびに集計していた。
ローカル保存では保存先ディレクトリ全体を走査する（画像3万件で490ms）。

**影響**　件数に比例して悪化する。3年ぶん（画像9万件）では約1.5秒。
さらに **S3 運用ではバケット全体を `ListObjectsV2` でページングする**ため、
ホーム画面を開くたびにAPI呼び出しが発生し、遅いうえに課金される。

**対応**　使用量を短時間キャッシュするようにした（既定300秒、`BCARDS_STORAGE_USAGE_CACHE_SECONDS`）。
容量アラートの判定に使う値であり、秒単位の正確さは不要なため。
管理画面には「いま集計し直す」を用意し、正確な値も取れるようにしてある。

**結果**　ホーム画面 551 ms → **41 ms**。

あわせて、管理画面のストレージ内訳が画像レコードを全件メモリに読み込んでいたのを
SQL の集計（`GROUP BY variant`）に変更した。

### 4.2 CSV出力が名刺1件ごとに連絡先を読み直していた（N+1）

**現象**　1万件のCSV出力に 12.05 秒。

**原因**　CSVの電話・携帯・FAX・メール・URL 列は `card.contact_values()` を参照するが、
連絡先が遅延読み込みのままで、名刺1件につき1クエリ発行されていた。

**影響**　件数に正比例する。同期のHTTPリクエスト内で実行されるため、
件数が増えるとリバースプロキシのタイムアウトに達する。

**対応**　CSV出力の経路で連絡先をまとめて読む（`selectinload`）ようにした。

**結果**　12.05 秒 → **2.85 秒**（約4倍）。

> どちらも自動テストでは見つからず、本番相当のデータ量を投入して初めて表面化した。
> 再発防止として、**発行されるクエリ数と集計の呼び出し回数**を検証する
> 回帰テストを追加した（`app/tests/test_performance_guards.py`）。
> 実行時間そのものを測るテストは環境差で不安定になるため採用していない。

## 5. 非機能要件への反映（提案）

| 項目 | 現在の記載 | 提案 | 根拠 |
| --- | --- | --- | --- |
| 検索応答時間 | 1万件規模で2秒以内（要確定） | **1万件規模で1秒以内**（実測337ms） | §2 |
| RTO | 4営業時間（初期案） | **2営業時間**（実測1分＋人的対応の余裕） | §3 |
| RPO | 24時間 | 24時間（据え置き） | 日次バックアップ |
| CSV出力（1万件） | 記載なし | **10秒以内**（実測2.85秒） | §4.2 |

RTO を短縮できるのは「復元作業そのものが速い」ためであり、
障害の検知と判断にかかる時間は別途見込む必要がある。
決裁の際は、**業務上どれだけ止まってよいか**から決め、
実測値はその目標が技術的に達成可能かの裏付けとして使うのが適切である。

## 6. 同時アクセス時の応答（追加測定）

§2 は単一利用者の値である。実運用で問題になるのは
「複数人が同時に検索し、その裏で誰かが名刺を取り込んでいる」場面のため、
要件§5 の想定（利用者10名・うち同時取込2名）に合わせて測り直した
（`app/ops/bench_concurrent.py`、各条件30秒）。

### 名刺1万件（＝約3.3年ぶん。現実的な規模）

| 条件 | 実行回数 | 中央値 | p95 | 最悪値 |
| --- | --- | --- | --- | --- |
| 検索5人 | 1,022 | 134 ms | 239 ms | 301 ms |
| 検索5人 ＋ 取込2人 | 1,005 | 143 ms | 235 ms | 322 ms |

**取込が走っていても検索は約7%しか遅くならない。** これは §4 で
`OMP_THREAD_LIMIT=1` を設定し、OCRがCPUを占有しないようにした効果である。
この設定が無い場合、OCRがCPUを使い切って検索が待たされる。

### 名刺10万件（＝約33年ぶん。参考）

| 条件 | 実行回数 | 中央値 | p95 | 最悪値 |
| --- | --- | --- | --- | --- |
| 検索5人 | 116 | 1,399 ms | 1,806 ms | **2,255 ms** |
| 検索5人 ＋ 取込2人 | 100 | 1,631 ms | 2,144 ms | **2,498 ms** |

10万件では、**単独の応答時間より先に同時実行が限界に来る**。
単独では最悪909ms（§7）だが、5人同時では2.2秒に達し、要件（2秒以内）を超える。
4CPUの環境で、1回の検索が並列シーケンシャルスキャンを行うため、
5人ぶんでCPUを使い切ってしまうことによる。

これは索引では解決しない。必要になった段階で、CPU増強か
全文検索方式への変更（後述）を検討する。年間3,000枚の想定では
10万件に達するのは30年以上先であり、現時点で対応する必要はない。

## 7. 10万件規模での測定と対策（今後の課題1の検証）

初版で「10万件規模になると2秒に近づく見込み」と書いた**予測を実測で検証した**。

### 予測は当たっていた（想定より悪かった）

| 処理 | 1万件 | 10万件（対策前） | 判定 |
| --- | --- | --- | --- |
| キーワード検索（氏名） | 221 ms | 748 ms | OK |
| キーワード検索（会社名） | 230 ms | 1,095 ms | OK |
| キーワード検索（電話番号） | 204 ms | 790 ms | OK |
| **キーワード検索（該当なし）** | 216 ms | **2,158 ms** | **要件超過** |
| 一覧＋総件数 | 65 ms | 325 ms | OK |

該当がない検索が最も遅い。**該当がある場合は `LIMIT 50` で早期に打ち切れるが、
該当なしの場合は全件を走査しきるまで終わらない**ためである。

### 効いた対策は1つだけだった

`pg_trgm` の GIN インデックスを7本（氏名・会社名・部署・役職・連絡先など）張って測定し、
その後1本ずつ外して切り分けた。

| 索引の構成 | 該当なし検索（最悪値） |
| --- | --- |
| 索引なし | 2,158 ms |
| 7本すべて | 357 ms |
| **`card_contact.value_raw` の1本だけ** | **386 ms** |
| その1本も外す | 1,627 ms |

**`card_contact.value_raw` への1本だけが効いていた。** 残り6本は数値に影響しない。

理由は実行計画で確認した。氏名・会社名などの条件は
`person` / `company` / `business_card` に**またがる OR** のため、
PostgreSQL は「結合してから絞り込む」計画を選び、列ごとの索引を使えない。
一方、連絡先は `card_contact` 単独の条件（`IN` サブクエリ）なので索引が効く。
名刺10万件に対して連絡先は40万件あり、ここの全走査が支配的だった。

> 「`pg_trgm` を入れれば速くなる」は**この設計では正しくない**。
> 効くのは単一テーブルに閉じた条件だけである。

### 対策後

| 処理 | 対策前 | 対策後 |
| --- | --- | --- |
| キーワード検索（該当なし） | 2,158 ms | **382 ms** |
| キーワード検索（電話番号） | 790 ms | **343 ms** |
| キーワード検索（氏名） | 748 ms | 909 ms（変化なし） |
| キーワード検索（会社名） | 1,095 ms | 908 ms（変化なし） |

索引はマイグレーション `d72f96ac9ae1` で適用済み。
サイズは連絡先40万件で 13MB、作成は数秒。書き込みは年間3,000件程度のため
索引更新の負荷は無視できる。

**PostgreSQL 専用**で、SQLite では何もしない。また `pg_trgm` の作成には
スーパーユーザー権限が要るため、権限が無い場合は索引を見送って
マイグレーション自体は成功させる（メッセージで手順を案内する）。

### 氏名・会社名の検索を速くするには

複数テーブルにまたがる OR が残る限り、索引では速くならない。
必要になった場合の選択肢は次のとおり。**現時点では不要。**

| 案 | 内容 | 影響 |
| --- | --- | --- |
| 検索用の列を持たせる | `business_card` に氏名・会社名等を連結した列を作り、GIN索引を1本張る | 書き込み時の更新処理が必要。設計変更を伴う |
| 全文検索へ変更 | `tsvector` ＋ 形態素解析（日本語は追加拡張が必要） | 部分一致の挙動が変わる。利用者への影響あり |
| CPU増強 | 同時実行の限界を上げる | 最も安価。10万件・5人同時なら有効 |

## 8. 今後の課題

1. **S3 運用での再測定**　本測定はローカル保存での値。オブジェクトストレージでは
   画像の取得・保存にネットワーク遅延が加わる。
2. **CSVの非同期出力**（論点I）　1万件で2.85秒なら同期出力で足りる。
   非同期化は当面不要と判断できる（対応済みの判断）。
3. **10万件に達した場合の対応**　§7 のとおり、索引では解決しない領域が残る。
   到達は30年以上先の見込みだが、途中で運用が変わって件数が跳ねた場合に備え、
   監視項目に検索応答時間を入れてある（[運用手引き §10](./operations-guide.md#10-監視項目)）。

## 再現手順

```bash
cd business-card-system/app

# 1. 検証用データベースを用意する（本番では絶対に実行しないこと）
createdb bcards_bench
export BCARDS_DATABASE_URL="postgresql+psycopg://bcards:***@127.0.0.1:5432/bcards_bench"
export BCARDS_STORAGE_DIR=/tmp/bench-objects
.venv/bin/alembic upgrade head
PYTHONPATH=src .venv/bin/python seed.py

# 2. 本番相当のデータを投入する（1万件・画像つきで約8分）
PYTHONPATH=src .venv/bin/python ops/loadgen.py --cards 10000

# 3. 応答時間を測る（単独）
PYTHONPATH=src .venv/bin/python ops/bench.py --out capacity.md

# 3b. 同時アクセス時を測る（検索5人＋取込2人）
PYTHONPATH=src .venv/bin/python ops/bench_concurrent.py --readers 5 --importers 2 --seconds 30

# 4. バックアップ・復元の所要時間を測る
time ./ops/backup.sh
time ./ops/restore.sh /var/backups/bcards/<取得日時> --force
time PYTHONPATH=src .venv/bin/python ops/verify.py
```

`ops/loadgen.py` は `BCARDS_ENV=production` のときは実行を拒否する。
