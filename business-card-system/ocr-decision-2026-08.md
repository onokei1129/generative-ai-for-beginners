## 2. いちばん重要な発見：LLMでは直らない

**前回の報告では「改善の本命はLLMによる項目分離」と書きました。これは現時点では正しくありません。**

理由を測りました。項目が取れなかったとき、原因は2つに分かれます。

- **取り出しの失敗** … OCRは正しく読めているのに、どの項目か判定を誤った
- **読み取りの失敗** … OCRがその文字を読めていない（そもそも文字列が存在しない）

LLMによる項目分離は、**OCRが読んだ文字を受け取って項目に分ける**仕組みです。読み取りに無い文字は作れません。したがって直せるのは前者だけです。

正解のある259項目で切り分けた結果：

| 分類 | 件数 | 割合 | LLMで直るか |
| --- | ---: | ---: | --- |
| 正解 | 164 | 63.3% | — |
| 取り出しの失敗 | 9 | **3.5%** | **直りうる** |
| 読み取りの失敗 | 86 | **33.2%** | **直らない** |

> **LLMによる項目分離の効果は、上限で +3.5ポイントです。**
> 残り 33.2% は読み取りの問題で、LLMをいくら良くしても届きません。

前回「本命」と判断したのは、当時のルールベース抽出が弱く、取り出しの失敗が多かったためです。その後の修正で取り出し側がほぼ出尽くし、**ボトルネックが読み取り側へ移りました**。

（注：この 63.3% は「正解が空でない項目」だけを分母にした値です。§1 の 68.0% は空欄も正解として数えるため分母が異なります。同じ測定の別の見方で、矛盾ではありません。）

### 実例

実テストの3枚目（韓国の方の名刺）で、カタカナの氏名が取れませんでした。

```
印字   ユン　ソクン
読み   dy  ソクン        ← 「ユン」が「dy」と誤読
```

`ユン` という文字が読み取り結果に存在しないため、項目分離では作れません。この名刺では、ラテン文字の `SEOKHOON YOON` を代わりに使うよう直しました（対処であって、解決ではありません）。

### 画像処理では直りませんでした

「暗い背景の白抜き文字だから」という仮説を立て、反転処理の効果を測りましたが、**効果はありませんでした**。

| 条件 | `ユン` | `ソクン` |
| --- | --- | --- |
| 明背景・きれい | ○ | ○ |
| **暗背景・きれい** | **○** | **○** |
| 暗背景・きれい ＋ 反転 | ○ | ○ |
| 明背景・写真ふう | × | × |
| 暗背景・写真ふう | × | × |
| 暗背景・写真ふう ＋ 反転 | × | × |
| 〃 ＋ 自動コントラスト／2倍・3倍拡大／シャープ | × | × |

暗背景そのものは原因ではなく（きれいなら読める）、崩れるのは**撮影品質**でした。反転・コントラスト調整・拡大・シャープのいずれも1項目も改善しないため、**コードは変更していません**。

## 3. 案ごとの評価

### 案1：現状のまま

項目正答率 68.0%、1枚あたり4.2項目を手で直す計算です。年3,000枚なら年12,600項目の手修正。**追加費用ゼロ・画像は社外に出ません。**

### 案2：ローカルOCRの差し替え（推奨）

PaddleOCR・EasyOCR を tesseract の代わりに使い、同じ指標で比較します。**アダプタと計測の仕組みは実装済み**（`poc/runner.py` の構成F・G）で、インストールするだけで測れます。

- **費用ゼロ、契約不要、画像は社外に出ません**（ローカルで動作）
- 読み取りの失敗 33.2% に直接効く可能性がある唯一の無料の手
- 導入コストは各1〜3GBのインストールのみ。依存が大きいため `requirements.txt` には入れていません
- **効果は未知数です。** 測って初めて分かります

**これを先に測るべき理由**は、費用も法務確認も要らないのに、いま効く可能性がある唯一の選択肢だからです。ここで十分な精度が出れば、案3・案4の検討自体が不要になります。

### 案3：LLMによる項目分離

`ANTHROPIC_API_KEY` が必要です。アダプタは実装済み（構成E）。

費用（1枚あたり 入力1,500トークン・出力300トークンで試算）：

| モデル | 1枚あたり | 年3,000枚 |
| --- | ---: | ---: |
| Haiku 4.5 | $0.003 | **$9（約1,400円）** |
| Sonnet 5 | $0.009 | $27（約4,100円） |
| Opus 5 | $0.015 | $45（約6,800円） |

（1ドル150円換算。急ぎでない処理はバッチAPIで半額になります。）

**費用は問題になりません。** 問題は効果が上限 +3.5ポイントにとどまることです。**画像は送信せず、OCRが読んだ文字のみを送ります**が、名刺の文字は個人情報のため、外部送信の可否は確認が必要です（[personal-data-handling-v0.3.md](./personal-data-handling-v0.3.md)）。

### 案4：クラウドOCR（Azure / Google / AWS）

読み取りの失敗 33.2% に効く可能性が最も高い選択肢です。ただし：

- **画像そのものを社外へ送ります。** 法務・総務の確認が必須です
- 名刺専用モデルは主要クラウドから減っており、汎用OCR＋項目分離の組み合わせになります（[open-issues-v0.3.md 論点C](./open-issues-v0.3.md) の調査結果）
- 費用は従量課金。選定時点の料金表で見積もりが必要です
- 認証情報が無いため**未計測**です

## 6. 案2の実施結果（2026-08-02）

### 結論

**単純な差し替えでは改善しませんでした。2つのエンジンを併用すると改善しました。**

| 構成 | 項目正答率 | 1枚あたり修正項目数 | 処理時間/枚 |
| --- | ---: | ---: | ---: |
| D 現行（tesseract） | 68.0% | 4.2 | 3.4 秒 |
| G EasyOCR に差し替え | 64.1% | 4.7 | 12.6 秒 |
| **H EasyOCR と tesseract の併用** | **74.9%** | **3.2** | **14.9 秒** |

**費用ゼロ・契約不要・画像は社外に出ません**（すべてローカル）。

### なぜ併用が効くのか

差し替えただけの構成Gは、総合では現行を下回りました。しかし項目ごとに見ると、**得意・不得意がきれいに分かれていました**。

| 項目 | D tesseract | G EasyOCR |
| --- | ---: | ---: |
| せい／めい（かな） | 65% | **80%** |
| 郵便番号 | 75% | **90%** |
| 電話 | 85% | **95%** |
| 携帯 | 57% | **79%** |
| メール | **70%** | 20% |
| URL | **46%** | 8% |
| 住所 | **90%** | 65% |

原因は読み取り結果を見て特定しました。

**EasyOCR は英数字の記号を落とします。**

```
正解      takahashi@hokkaido-foods.example
EasyOCR   takahashi@hokkaido-foodsexample      ← ドットが消える
正解      https://logi-kyushu.example
EasyOCR   https:Illogi-kyushuexample           ← // が Il、ドットが消える
```

**tesseract は日本語を1字ずつ切ります。**

```
正解      株式会社ロジスティクス九州
tesseract 株 式 会 社 ロ ジス ティ クス 九州
EasyOCR   株式会社ロジスティクス九州            ← 正しい
```

弱点が重なっていないため、両方かけて項目ごとに取れたほうを採ると、両者を上回ります。FAX は 75%・50% がそろって **100%**、メールは 70%・20% が **75%** になりました。

### 併合の規則

**EasyOCRの値を優先し、空のときだけ tesseract の値を使う** — これだけです。「メールとURLは tesseract に任せる」のように項目ごとに担当を決める案も測りましたが、**差はありませんでした**。単純なほうを採っています。

1つだけ例外を設けています。メールとURLは、EasyOCRが**空ではなく「もっともらしい誤り」**を返すことがあるため、形が壊れていれば tesseract の値に譲ります。空欄なら人が気づきますが、それらしい誤りは気づかれずに登録されるためです。この検査で正答率は変わりません（防いでいるのは点数ではなく、見逃される誤りのほう）。

なお、`example.co.jp` の途中のドットが落ちて `exampleco.jp` になった場合は、メールの形として正しいため**見分けられません**（実測でも3件）。読み取りの誤りを後段で完全に救うことはできません。

### 代償

| | 現行 | 併用 |
| --- | ---: | ---: |
| 処理時間／枚 | 3.4 秒 | **14.9 秒**（約4.4倍） |
| 追加のインストール | — | **約1.5GB**（EasyOCR＋PyTorch） |

取込はキュー方式で背後で進むため、**利用者の待ち時間は変わりません**（アップロードの応答は実測0.05秒／3ファイル）。年3,000枚なら1日あたり十数枚で、処理時間の増加は運用上の問題になりません。

### 悪化した項目が1つあります

**住所は 90% → 65% に下がりました。** この項目だけは tesseract のほうが良く、併用でEasyOCRの値を採るため悪化します。

住所だけ tesseract を優先すると、合成サンプルでは 65% → 90% に戻ります（実測）。**ですが採用しません。** 理由は次のとおりです。

合成サンプルでのEasyOCRの失敗5件は、すべて写真品質の画像での1文字ずつの誤読でした。

```
正解  福岡県福岡市博多区博多駅前4-4-4
読み  福岡原福岡市性多区博多駅前4-4-4     ← 県→原、博→性
```

住所はいちばん長い項目なので、1文字あたりの誤読率の差がここに最も強く出ます。ここまでは筋が通っています。

**しかし実名刺では逆でした。** 実テスト9枚目（Causal Foundry）では、

| | |
| --- | --- |
| EasyOCR | `東京都渋谷区恵比寿南1-1-1`（正しい） |
| tesseract | `〒4 ら の - の 9 の 22`（読み崩れ） |

tesseract を優先していたら、この名刺は悪化していました。**合成サンプル20枚の結果は一般化しません。** 項目ごとの担当は、実名刺の正解ラベル（決裁事項4）が揃ってから決めます。

### PaddleOCR は計測できませんでした

インストールは成功しましたが、**モデルの重みの配布元がこの検証環境の通信ポリシーで遮断されており**、動かせませんでした（HuggingFace・ModelScope・Baidu の各配布元がすべて拒否）。

コード側の問題ではありません。配布元へ到達できる環境で `python -m poc.runner --only F` を実行すれば、同じ指標で計測されます。EasyOCR は同じ手順で動いたため、**仕組みは正しく、環境の制約です。**

### 使えるようにしたもの

**2026-08-02 に決裁いただき、併用構成を既定にしました。**

| | |
| --- | --- |
| アプリ | **既定が `combined`。** 従来の構成に戻す場合は `BCARDS_OCR_PROVIDER=tesseract` |
| インストール | `pip install -r requirements-combined.txt`（Windows は `setup.bat` が自動で実行） |
| 計測 | `python -m poc.runner --only H` |
| 確認画面 | 「OCRが読んだ文字を見る」に両エンジンの結果を別々に表示（どちらが読めたか分かるように） |

片方のエンジンが使えない環境では、動くほうだけで続けます。両方だめなときは擬似OCRで代替せず失敗させます（擬似OCRの値を読み取り結果として保存しないため）。

**既定にしたことで新しい危険が1つ生まれます。** EasyOCR は依存が大きく（約1.5GB）自動では入らないため、入れ忘れた環境では tesseract だけで動き、**見た目は正常なまま精度が 68.0% に戻ります**。動くので気づけません。そこで次の2か所で知らせるようにしました。

- **起動時の設定チェック** — 使えないエンジンと、戻る精度（74.9% → 68.0%）を出す
- **`python -m poc.doctor`（動作確認）** — `[ -- ]` として理由とインストール手順を出す。取込自体は動くので `[ NG ]` にはしない

### これで論点Cはどうなるか

| | |
| --- | --- |
| 前回の見通し | LLM項目分離の効果は上限 **+3.5ポイント** |
| 今回の実測 | エンジン併用で **+6.9ポイント**（費用ゼロ） |

**読み取り側の改善が、やはり効きます。** ただし 75.3% は依然として実用水準ではありません（1枚あたり3.2項目の手修正）。残る大きな失敗は縦書き（修正 7.5〜11.0 項目／枚）で、ここは案4（クラウドOCR）の検討が要ります。

### 実テストで見つかった不具合（10・11枚目）

案2の計測と並行して、実テストの報告を4件直しました。**いずれも合成サンプルの
点数は動きません**（このノイズが合成サンプルに無いため）。直したのは点数では
なく、**読めていないものを項目に入れてしまうこと**です。

| 枚目 | 症状 | 原因 |
| --- | --- | --- |
| 10 | 姓『にロニ』名『エニ』 | 飾りが `に ロニ エニ` と読まれ、それを氏名にしていた |
| 10 | 〃（対処後に別の断片が入る） | `Game Business Development`／`ee BO`／`スー` が順に氏名になった |
| 11 | 会社名が空 | 行頭の `x)` でドメイン照合（`edgecre` ← `Edge Creators`）が外れていた |
| 8・9 | 「OCRの結果はありません」 | 誤った説明。保存済みではOCRを実行していないだけ |

10枚目は**氏名を1文字も読めていない**ため、結果は空欄になります。`German` と
`Kurnikov` は別々の行にあり、1行1語では氏名と判断できません。空欄なら入力する
人が気づきますが、それらしい誤りは気づかれずに保存されます。

8・9枚目は、欄を開いたときにOCRの文字を取りに行くようにしました。保存した値の
誤りに気づいたとき（9枚目の住所が `〒4らの - の９の` になっていた）、何をどう
読み違えたのかを画面で確かめられます。

### 実テストで見つかった不具合（8・9枚目）

読み取り自体は成功しているのに項目にならない、という種類が4件ありました。
**いずれも合成サンプルの点数は動きません**（D 68.0% / H 74.9% のまま）。

| 枚目 | 症状 | 原因 |
| --- | --- | --- |
| 8 | 郵便番号が空、住所の末尾に `06267` | 郵便番号の判定が日本の形（3桁-4桁）だけだった |
| 9 | 郵便番号が空 | `〒150‐0022` の横棒が ASCII のハイフンでない字だと判定が外れる |
| 9 | 携帯が `+81-70-1508-9897` | 日本の番号の国際表記を国内表記へ直していなかった |
| 9 | 住所に建物名が入らない | `ヒューマックス恵比寿ビル8F` が次の行にあるとつながらなかった |

**横棒の件は、他の名刺にも効きます。** `‐`（U+2010）や `–`（U+2013）など7種類が
ハイフンとして扱われず、郵便番号も電話番号も空になっていました。画面には
「読めた文字」として正しく出るため、**読めているのに項目にならない**という、
いちばん原因の見えにくい形の失敗です。

なお8枚目の `06267` は、以前**意図して住所に残していました**（「韓国の5桁は
日本の郵便番号の欄に入れない」）。利用者から郵便番号が取れていないという
報告を受けて改めています。名刺に印字された郵便番号は郵便番号の欄に入るのが
