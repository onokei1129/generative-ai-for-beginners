## 論点A：名刺の編集権限

要件 §7 で3案が併記されている。

### 選択肢の比較

| 比較軸 | 案1 全利用者が編集可能 | 案2 登録者と管理者のみ編集可能 | 案3 修正申請＋管理者承認 |
| --- | --- | --- | --- |
| 誤操作リスク | 高い（ただし履歴で復旧可） | 中 | 低い |
| 情報の鮮度 | 高い（気づいた人がすぐ直せる） | 中（登録者が退職すると更新不能） | 低い（承認待ちが滞留） |
| 管理者の運用負荷 | 小 | 小 | **大**（10名規模でも承認が常時発生） |
| 退職者登録データの保守 | 問題なし | **問題あり**（登録者が編集できない） | 問題なし |
| 実装コスト | 小 | 小 | 大（申請・承認・通知・差戻し画面が必要） |
| 監査性 | 履歴があれば十分 | 同左 | 最も高い |
| 10名規模での適合度 | ◎ | △ | △ |

### 推奨

**案1（全利用者が編集可能＋全変更を履歴保持）** を採用する。要件 §7 の「初期推奨」と同じ。
ただし、案1のままでは影響の大きい操作まで全員が実行できるため、**操作単位でガードをかける**。

| 操作 | 一般利用者 | 管理者 |
| --- | --- | --- |
| 項目の修正（誤字・連絡先更新等） | ○ | ○ |
| 新しい名刺の追加登録 | ○ | ○ |
| 既存名刺の上書き・置換 | ○（確認ダイアログ＋変更理由の入力必須） | ○ |
| 名刺の論理削除 | ○（変更理由の入力必須） | ○ |
| 人物・会社の統合（マージ） | ✕ | ○ |
| 削除済み名刺の復元 | ✕ | ○ |
| 完全削除 | ✕ | ○ |

### 決定に必要な確認事項

1. 変更理由の入力を**必須**とするか、任意とするか（必須にすると運用が重くなる。上書き・削除のみ必須が折衷案）
2. 案3へ将来移行する条件を決めておくか（例：利用者20名超、または誤編集の申告が月3件を超えた場合に再検討）
3. `app_setting.card_edit_policy` で切替可能にしておく前提でよいか（推奨：切替可能にする）

## 論点B：クラウド事業者の選定

要件 §5 は「AWS、Microsoft Azure、Google Cloud等から、開発環境およびOCRサービスとの親和性を踏まえて選定する」としている。

### 比較

| 比較軸 | AWS | Microsoft Azure | Google Cloud |
| --- | --- | --- | --- |
| 主なOCR | Amazon Textract | Azure AI Document Intelligence | Document AI / Cloud Vision |
| 名刺特化の既製モデル | なし（汎用OCR＋独自抽出） | **v4.0 以降で名刺プリビルトモデルは非対応**（後述） | なし（汎用OCR＋独自抽出） |
| 認証基盤 | Cognito / IAM Identity Center | **Microsoft Entra ID**（M365 契約があれば追加コストが小さい） | Cloud Identity |
| 条件付きアクセス（IP制限・MFA） | 実装可（WAF＋Cognito等） | **Entra ID の条件付きアクセスで要件 §6 をほぼ標準機能で実現** | 実装可（Context-Aware Access） |
| オブジェクトストレージ | S3 | Blob Storage | Cloud Storage |
| 国内リージョン | 東京・大阪 | 東日本・西日本 | 東京・大阪 |
| 小規模構成のコスト | 同程度（10名規模では差は小さい） | 同程度 | 同程度 |
| 社内の運用ノウハウ | **要確認** | **要確認** | **要確認** |

### 推奨と判断基準

- **決め手はOCRの精度そのものではなく、①既存の社内ID基盤 ②開発・運用の慣れ** と考える。10名規模では月額コスト差は数千円規模に収まる見込みで、コストは決定要因になりにくい。
- 社内で **Microsoft 365 / Entra ID を利用している場合は Azure を第一候補**とする。要件 §6（社内IPからのみ／管理者のみ社外＋MFA／無操作ログアウト／ログイン失敗履歴）を、アプリ実装ではなく認証基盤の標準機能で満たせるため、実装量と将来の運用負荷が最も小さい。
- Entra ID を使っていない、または既存システムが AWS 中心であれば **AWS** を選ぶ。この場合、条件付きアクセス相当はアプリ＋WAFで実装する必要がある（見積に反映すること）。
- OCRは事業者をまたいで利用できる（例：AWS上のアプリから Google Document AI を呼ぶ）ため、**クラウド事業者とOCRサービスは別々に決めてよい**。

### 決定に必要な確認事項

1. 現在利用している社内ID基盤（Entra ID / Google Workspace / その他）
2. 既存システムのクラウド利用実績と運用担当者のスキル
3. データ保存地域を国内に限定する必要があるか（社内規程・取引先との契約条件）
4. 年間の想定予算上限

## 論点C：OCRサービスの選定

要件 §8 の確認項目に沿って整理する。

### 重要な前提（調査結果）

**名刺専用のプリビルトモデルは主要クラウドから減少している。**
Azure AI Document Intelligence の名刺モデル（`prebuilt-businessCard`）は **v4.0 以降でサポートされない**（v3.1 までの機能）。加えて、プレビュー版APIは 2026年6月30日 を期限に v4.0 GA への移行が必要とされている。
AWS Textract・Google Document AI にも名刺専用モデルはなく、いずれも汎用OCR＋項目抽出の組み合わせになる。

したがって、選定は「名刺プリビルトモデルがあるか」ではなく、**「汎用OCRの日本語精度」×「項目分離をどう実装するか」** の比較になる。

### 実装方式の選択肢

| 方式 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| 方式1 汎用OCR＋ルールベース抽出 | OCRのテキスト＋座標から、正規表現・辞書で氏名／会社名／役職等を判定 | 追加費用が小さい、挙動が予測可能 | レイアウト依存で精度が頭打ち。ルール保守が継続的に発生 |
| 方式2 **汎用OCR＋LLMによる項目分離** | OCR結果をLLMに渡し、構造化JSONで項目を得る | 日本語・縦書き・レイアウト崩れに強い。ルール保守が不要 | LLM API費用が加算。出力の安定化にプロンプト設計が必要 |
| 方式3 名刺特化の国内SaaS | 名刺データ化に特化した外部サービスを利用 | 日本語名刺の精度が期待できる | データの外部保持・学習利用の条件確認が必須（§8）。API提供の有無・費用は要確認 |

**第一候補は方式2。** 要件 §8 の「氏名、会社名、役職等の項目分離」「縦書き対応」を、ルール保守なしで満たしやすい。要件 §8 は「OCR結果は自動確定せず利用者が確認・修正する」前提のため、方式2の出力ゆらぎは確認画面で吸収できる。

### 事業者比較（要件 §8 の確認項目）

| 確認項目 | Azure AI Document Intelligence | Google Document AI / Vision | Amazon Textract | 国内名刺特化SaaS |

| 日本語認識精度 | 良好（要PoC） | 良好（要PoC） | 日本語対応は他2社に比べ限定的。**要PoC** | 名刺用途では有力。要PoC |
| 縦書き対応 | **要検証** | **要検証**（縦書きは苦手との指摘あり） | **要検証** | **要確認** |
| 英語対応 | ○ | ○ | ○ | 要確認 |
| レイアウト解析 | ○（レイアウト／座標情報あり） | ○ | ○ | ○ |
| 項目分離 | 名刺プリビルトは非対応 → カスタム抽出／LLM併用 | 汎用のため LLM 併用前提 | 汎用のため LLM 併用前提 | 標準機能 |
| 画像データの保存有無 | **契約・設定で要確認** | **要確認** | **要確認** | **要確認（最重要）** |
| 学習利用の有無 | **要確認（オプトアウト可否）** | **要確認** | **要確認** | **要確認** |

| API利用料金 | **要見積**（従量課金） | **要見積** | **要見積** | **要見積** |
| 処理速度 | 要PoC | 要PoC | 要PoC | 要PoC |
| 障害時の再処理 | リトライ実装＋`import_item` の再処理で対応 | 同左 | 同左 | 要確認 |

### PoCの実施状況

**第1回PoCを実施した。結果は [ocr-poc-report.md](./ocr-poc-report.md) を参照。**

計測用のコードは `app/poc/` にあり、実名刺が用意できれば `--real` オプションで同じ指標を再計測できる。

第1回で分かったこと（合成サンプル16枚）：

- 現行のルールベース抽出（方式1）の項目正答率は **44.8%**、1枚あたり **7.2項目**の修正が必要
- 表示用の画像補正をOCRにも掛けていたことが精度を **10.5ポイント**下げていた（修正済み）
- 縦書き名刺とふりがなが最も弱い（ふりがなは0%）

**その後（実テスト227枚を経た現在）：**

- 項目正答率 **68.0%**、1枚あたりの修正項目数 **4.2**（合成サンプル20枚）
- **本書が第一候補としていた方式2（LLM抽出）の効果は、上限 +3.5ポイント**と判明した。
  取れなかった項目の内訳は「取り出しの失敗 3.5%」に対し「読み取りの失敗 33.2%」で、

- したがって、いま効く手は**読み取りエンジン側**にある

**案2（ローカルOCRの比較）を実施した結果（2026-08-02）：**

### 残りの進め方

1. 実際の名刺 **30〜50枚**（縦書き・英語併記・ロゴ多め・スマホ撮影・複合機スキャンを含む）をサンプルとして用意する
2. 候補2〜3サービス × 方式1/方式2 で処理し、以下を測定する
   - 項目別の正答率（氏名／会社名／部署／役職／電話／メール／住所）
   - 1枚あたりの処理時間
   - 1枚あたりの費用
   - 確認画面での修正操作回数（＝実運用の手間）
3. **項目別正答率と修正の手間**で決定する。総合正答率だけで決めない（氏名・会社名の誤りは修正コストが大きい）

> 手順2・3は `app/poc/runner.py` が自動で行う。手配が必要なのはサンプルと各サービスの認証情報のみ。

#### スキャンフォルダからの名刺の抽出

サンプルの供給元として ScanSnap の保存フォルダを使う場合、**領収書などの書類が混在している**。
そのままPoCに掛けると領収書まで名刺として採点されるため、先に仕分けを行う
（`app/poc/classify.py`）。外部サービスへ送信せず、ローカルだけで完結する。

判定は「形状（名刺は縦横比 約1.65）」と「文字（領収書系の語／名刺系の語）」の
スコアを合算し、名刺／領収書／**不明** に分ける。迷ったものは自動で振り分けず
不明として人の確認に回す。領収書を名刺として通すほうが実害が大きいためである。

合成サンプル28件（名刺16・領収書12）での実測値：

| 条件 | 正答 | 不明（要目視） | **誤判定** |
| --- | --- | --- | --- |
| 形状＋文字（既定） | 28/28（100%） | 0 | **0** |
| 形状のみ（`--no-ocr`） | 0/28（0%） | 28 | **0** |
| 余白つき・傾きあり（形状が使えない条件） | 19/28（67.9%） | 9 | **0** |

- 形状の手がかりが失われても、誤判定ではなく「不明」に落ちる。想定どおりの壊れ方をしている
- ただしこれは合成サンプルでの値であり、**実データでの精度は別途確認が必要**。
  `_truth.csv` を手で用意すれば `app/poc/classify_eval.py` で同じ数値が出せる

#### 実データで見つかった不具合（修正済み）

実際の ScanSnap フォルダで試したところ、**「領収書」と大きく印字されたJRの領収書が
名刺として通った**。原因は3つ重なっていた。

| 原因 | 内容 |
| --- | --- |
| OCRの失敗を握りつぶしていた | 例外を捕まえて空文字を返しており、**tesseractが動いていなくても「文字が無い」として続行**していた。形状だけの判定に落ちたことに気づけない |
| 縦横比の帯が重なっていた | 名刺帯(1.37〜1.93)がA4/A5帯(1.35〜1.48)を飲み込み、判定順の都合で**書類形状でも加点**されていた。問題の領収書は比1.47 |
| 形状だけで名刺と確定していた | 文字の裏づけが無くても、形状の+2.0だけで閾値に達していた |

修正内容:

1. **OCRが動かない場合は仕分け自体を中止する。** 開始前に1枚試して疎通を確認する
2. 縦横比は「細長い → 書類 → 名刺」の順に、重ならない帯として判定する
3. **文字の裏づけが無いまま「名刺」と確定しない**（「不明」に落として人が見る）

3の結果、`--no-ocr` の正答は 16/28 から 0/28 になったが、
**領収書を名刺と誤判定する件数は 4件 → 0件**になった。実害が大きいのは後者なので、
「当てにいかず人に投げる」方向へ倒している。回帰は `tests/test_classify_guard.py` で固定した。

### 実データでPoCを行う手順

手を動かしていただく必要があるのは **3.** の正解ラベル入力だけで、他は自動である。

```bash
cd business-card-system/app

# 1. スキャンフォルダから名刺だけを取り出す（領収書等を除く）
.venv/bin/python poc/classify.py "C:/Users/xxx/Dropbox/ScanSnap" \
    --copy-to ./poc/real-cards --copy-unknown --report sort.md

# 2. 「不明」に落ちたものを目視で振り分ける（poc/real-cards/unknown/ を確認）

# 3. 正解ラベルを入力する（画面が開く。1枚1〜2分、40枚で1時間強）
.venv/bin/python poc/label.py ./poc/real-cards
#    Excel で入力したい場合は poc/labels_csv.py で CSV に書き出して受け渡す

# 4. ルールベースの精度を測る
.venv/bin/python poc/runner.py --real ./poc/real-cards --out real-rule.md

# 5. LLM抽出の精度を測る（ANTHROPIC_API_KEY が必要）
ANTHROPIC_API_KEY=... .venv/bin/python poc/runner.py \
    --real ./poc/real-cards --only E --out real-llm.md
```

**正解ラベルは画像を見て確認する。** `poc/label.py` はOCRの結果を初期値として
入れておき（入力を速くするため）、人が触っていない欄を黄色で「未確認」と表示する。
未確認のまま保存すると `_unverified` として記録され、その正解ラベルで測ると
`runner.py` が警告を出す。**未確認を残したまま測ると実際より良い精度が出る**ので、
黄色の欄は必ず画像と見比べること。空欄から入力したい場合は `--no-prefill` を付ける。

### 決定に必要な確認事項

1. 名刺画像を外部サービスへ送信することについて、社内規程・取引先との契約上の制約はないか
2. 学習利用オプトアウトが契約上明示できるか
3. PoC用サンプル名刺を提供できるか（実データの利用可否を含む）
4. `ANTHROPIC_API_KEY` を手配できるか（LLM抽出の測定に必要）

## 論点D：重複人物の名寄せロジック

要件 §10 は「既存人物と同一人物である可能性がある場合、利用者に6つの選択肢を提示する」としているが、**「可能性がある」の判定方法が未定**。

### 推奨方式

自動統合は行わず、**スコアリングによる候補提示のみ**とする。

| 一致項目 | 重み（案） |
| --- | --- |
| メールアドレス（正規化後）完全一致 | 決定的（ほぼ同一人物とみなす） |
| 携帯電話番号（正規化後）完全一致 | 高 |
| 氏名（正規化後）完全一致 ＋ 会社名一致 | 高 |
| 氏名完全一致のみ | 中（同姓同名を考慮し単独では候補止まり） |
| 氏名かな一致 ＋ 会社名一致 | 中 |
| 会社名一致のみ | 低（候補にしない） |

- 閾値は `app_setting.duplicate_match_threshold` で調整可能にする
- 候補は最大5件まで表示し、**どの項目が一致したかを画面に明示**する（利用者が判断できるようにする）
- 「新しい人物として登録」を既定の選択とし、統合は利用者の明示操作でのみ行う（誤統合の復旧コストが高いため）

### 決定に必要な確認事項

1. 同姓同名・旧姓変更の実例がどの程度あるか
2. 誤って統合した場合の分離機能（アンマージ）を初期リリースに含めるか（推奨：含める。含めない場合は統合を管理者限定にする）

## 論点E：IPアドレス制限の実装層

| 選択肢 | 長所 | 短所 |
| --- | --- | --- |
| ネットワーク／WAF層のみ | アプリに到達させない。実装が単純 | 利用者・ロール単位の細かい制御が難しい |
| アプリ層のみ | 管理者の社外アクセス許可（§6）などロール別制御が容易 | アプリまでリクエストが到達する |
| **両方（推奨）** | 一次遮断＋ロール別制御を両立。監査ログに拒否記録も残せる | 設定箇所が2か所になり、変更手順の整備が必要 |

**推奨**：WAF層で許可レンジ外を一次遮断し、アプリ層でロール・利用者単位の判定と `login_attempt` への記録（`blocked_ip`）を行う。
管理画面からの許可IP登録（§6）はアプリ層の `allowed_ip` テーブルを更新し、WAF側は拠点・VPNの固定レンジのみを扱う運用が現実的。

## 論点G：画像補正の実装範囲

要件 §4 は11項目の補正・警告を挙げている。**当初は実装コストで段階分けを提案していたが、
実装した結果 11項目のうち10項目が入った**ため、論点は「何を作るか」から
「**この範囲で確定してよいか**」に変わっている。

| 機能 | 当初案 | 実装状況 | 備考 |
| --- | --- | --- | --- |
| 名刺外周の自動検出 | ◎ 必須 | **実装済み** | `detect_card_quads` |
| 台形補正 | ◎ 必須 | **実装済み** | `warp_quad` |
| 回転補正 | ◎ 必須 | **実装済み** | 微小な回転は補正しない（下限1.5度）。再サンプリングで文字が甘くなり、OCR精度が落ちるため |
| 明るさ・コントラスト補正 | ◎ 必須 | **実装済み** | CLAHE |
| 解像度不足の警告 | ◎ 必須 | **実装済み** | `quality_report` |
| ピンぼけの警告 | ◎ 必須 | **実装済み** | ラプラシアン分散 |
| PDF内の複数名刺の分割 | ◎ 必須 | **実装済み** | pypdfium2 |
| 表裏判定 | ○ 推奨 | **実装済み** | 利用者が手動で入れ替えられる |
| 複数名刺の分割候補表示 | ○ 推奨 | **実装済み** | 最大6枚。利用者が確認・調整できる |
| 影の軽減 | △ 次期 | **実装済み** | 背景を推定して割り戻す。当初案から前倒しになった |
| 背景除去 | △ 次期 | **未実装** | 外周検出＋切り抜きで代替済み。単独機能としては不要と判断 |

### 実装して分かったこと

**補正は「表示用」と「OCR用」で分ける必要がある。** 当初は1枚の補正画像を両方に使っていたが、
表示用に効かせた強い補正をOCRにも掛けると**精度が10.5ポイント落ちる**ことが実測で分かった
（[PoC報告](./ocr-poc-report.md)）。現在は次のように分けている。

| 用途 | 補正 |
| --- | --- |
| 表示・保管用 | 外周検出・台形補正・回転補正・明るさ・影の軽減をすべて適用 |
| OCR用 | 幾何補正のみ。強い明るさ補正と縦長→横長の自動回転は**掛けない**（縦書きを壊すため） |

**論点**：この範囲（背景除去のみ見送り）で初期リリースとしてよいか。
**追加の開発期間は発生しない**ため、当初案にあった「開発期間が延びる」という論点は解消している。

## 論点H：ログ・履歴の保存期間

要件§10 は名刺データに保存期限を設けないとしているが、ログの保存期間は記載がない。
ログを無条件に貯め続けるとDBが肥大化し、検索も遅くなる。一方で監査ログは
「誰がいつ何をしたか」を後から追うためのものであり、短期で消すと目的を果たさない。

### 対象ごとの整理

| 対象 | 性質 | 期間の考え方 | 決定 |
| --- | --- | --- | --- |
| 監査ログ（`audit_log`） | 操作の記録。件数が最も増える | 不正調査の遡及期間を確保しつつ、DBには置き続けない | **1年経過でアーカイブ、3年で破棄** |
| 変更履歴（`change_history`） | 名刺の変更前後。名刺データの一部 | 名刺に保存期限がない以上、履歴だけ消すと「いつ誰が変えたか」が追えなくなる | **無期限（アーカイブもしない）** |
| CSV出力ログ（`csv_export_log`） | 個人情報の持ち出し記録。監査ログと1対1 | 監査ログと同じ扱い | **監査ログに準じる** |
| ログイン履歴（`login_attempt`） | 認証の成否 | 監査ログと同じ扱い | **監査ログに準じる** |

### 件数の見積り

年間3,000枚（要件§3）・利用者10名の想定で、監査ログは
閲覧・検索・取込・登録・CSV出力を合わせて **年間おおよそ5〜10万件**。
1件あたり約1KBとして年間 50〜100MB 程度で、DBを圧迫するほどではない。
それでも期限を決めておくのは、運用が長期化したときに
「いつまで残すか」を後から決めるほうが難しくなるためである。

### 実装

- 期間は管理画面のシステム設定で変更できる
  （`audit_log_archive_after_days` 既定365 / `audit_log_retention_days` 既定1095）。
  いずれも `0` を指定すると、それぞれ「アーカイブしない」「無期限で保持」になる
- アーカイブは JSON Lines（gzip）でオブジェクトストレージへ書き出し、DBからは削除する。
  **書き出しに成功してから削除する**ため、途中で失敗してもログは失われない
- アーカイブの作成・破棄・ダウンロードは、それ自体が監査ログに残る
- 日次バッチ（`app/ops/archive_logs.py`）または管理画面から実行する
- 管理画面（`/admin/audit/archives`）で、DB上の件数・アーカイブ対象件数・
  アーカイブ一覧を確認し、個別にダウンロードできる

### 決定に必要な確認事項

1. 監査ログ3年で足りるか（社内規程・業界の要請・監査対応の遡及期間）
2. アーカイブの保管先を、名刺画像と同じストレージにしてよいか（別アカウントへ分けるか）
3. 破棄を自動で行ってよいか、それとも管理者の承認を挟むか
